> 版本：v0.6（…v0.5 = R16~R19 纳入；**v0.6 = 通用化重构与用户体系，见 §11**——§3/§4 中与项目抽象冲突的表述以 §11 为准）

## 1. 背景与目标

### 1.1 背景

- 现有系统以 DeerFlow 2.0 为宿主，无人机业务能力已全部沉淀为**框架无关**的
  FastMCP 服务（streamable-HTTP + `X-API-Key` 鉴权 + Nacos 注册 + 工具内
  confirm_token 人在环）。
- DeerFlow 作为 harness 的痛点已在实战中暴露：工具发现失败缓存跳过必须重启、
  skills 不热重载、Gateway 行为不可控（正式开发 README 排障①②）。
- 目标是自研 harness 层，将「组装与治理」的控制权收回，同时补齐 WorkBuddy
  的通用工作能力（浏览器、文档交付物、消息入口）。

### 1.2 需求清单（验收基线）

### 1.3 非目标

- 不做桌面 GUI 控制（操作任意桌面应用）——WorkBuddy 有此能力，但本框架场景
  以「调平台 API + 产出文档」为主，GUI 控制投入产出比低，列为远期。
- 不重写规划器 / 执行器等 agent 原语——采用成熟内核，自研集中在组装与治理层。
- 不替换已交付的演示版与正式版 MCP 层——它们保持不动。

## 2. 选型结论

### 2.1 内核：deepagents（LangChain 官方）+ LangGraph

| 候选 | 结论 | 理由 |
|---|---|---|
| **deepagents** | ✅ 选用 | 规划 / 子代理 / 虚拟文件系统 / 中间件 / interrupt / Agent Skills 全部内置且抽象最薄；与 DeerFlow 同属 LangGraph 生态，已有认知可迁移；MCP 经 `langchain-mcp-adapters` 直连 |
| DeerFlow 2.0 | ❌ 继续作宿主不符合「自研框架」目标 | harness 行为不可控（已踩坑）；但其沙箱 / 消息网关设计继续作参考实现 |
| AgentScope（阿里） | ❌ 备选 | Nacos/Higress 亲和度高，但 deep-agent 抽象（规划/虚拟FS/上下文工程）不如 deepagents 成熟，需自补的 harness 层更多 |
| CAMEL / Eigent | ❌ | 偏成品桌面应用，二开不如自研组装 |
| 裸 LangGraph | ❌ | 全部原语自己搭，工作量大且容易设计错；deepagents 即是官方搭好的这一层 |

**deepagents 提供的与需求的对应**（均为官方文档确认的能力）：

- `create_deep_agent(model, tools, system_prompt, middleware, subagents, interrupt_on, memory, checkpointer, store, skills, backend, ...)`（deepagents 0.7.5 实证参数，checkpointer 直接作为该函数参数传入）
- 子代理：`task` 工具派生、上下文隔离、每个子代理独立 model / tools / middleware → R1、R8
- `TodoListMiddleware`（`write_todos`）→ R2
- 虚拟文件系统多后端：StateBackend / FilesystemBackend / StoreBackend /
  CompositeBackend / Sandbox 后端（带 `execute`）→ R4、R6、R9
- `interrupt_on={"tool_name": ...}` 人在环 → R5
- Agent Skills 标准（SKILL.md + 渐进式披露）→ R4
- `memory=`（AGENTS.md）+ StoreBackend → R6
- LangGraph checkpointer（Postgres）→ R9

### 2.2 周边选件

| 能力 | 选件 | 状态说明 |
|---|---|---|
| MCP 客户端 | `langchain-mcp-adapters`（`MultiServerMCPClient`） | streamable_http + 每 server 自定义 headers（`X-API-Key`），官方 README 明确支持 |
| 文档技能 | **自写四技能为主路径**（python-docx / python-pptx / openpyxl / reportlab，按 Agent Skills 开放标准） | ⚠️ 评审更正：anthropics/skills 的 docx/pptx/xlsx/pdf license 禁止在 Anthropic Services 之外保留/使用副本，**代码不可引入**（内部使用亦不合规），仅可读其 SKILL.md 写法作公开规范参考 |
| 前端 | `langchain-ai/agent-chat-ui`（MIT，活跃） | 作基座二开；开发期连 `langgraph dev`，**生产连自建协议端点或 Aegra**（见 4.9）。（`deep-agents-ui` 2026-06 已归档，仅作面板设计参考） |
| 浏览器 | Playwright MCP（微软官方，`npx @playwright/mcp`） | stdio 或 `--port` 开 streamable HTTP，直接进 MCP 配置 → R13 |
| 持久化 | PostgreSQL（checkpointer + store） | `langgraph-checkpoint-postgres`（MIT）：`PostgresSaver` + `PostgresStore` |
| 沙箱 | P0 `LocalShellBackend`（受限目录）；P1 自研 Docker 沙箱后端或自托管 Daytona | 详见 4.4（评审更正：官方无现成 Docker 后端） |

分层原则：**deepagents 负责 agent 原语，自研代码只出现在五处**——
① 消息网关，② MCP 配置生成器（对接 Nacos 桥），③ 中间件（审计/模型路由），
④ 技能管理服务，⑤ 前端二开。其余为配置与技能内容。

## 4. 模块详设

### 4.1 框架核心（Runtime 组装）

```python
# core/agent.py（示意）
from deepagents import create_deep_agent
from langchain.chat_models import init_chat_model

lead_model = init_chat_model(
    "openai:qwen3-max", base_url=DASHSCOPE_COMPAT, api_key=DASHSCOPE_KEY)  # 见4.8

agent = create_deep_agent(
    model=lead_model,
    tools=mcp_tools,                      # 4.2 产出
    system_prompt=LEAD_PROMPT,            # 迁移自 DeerFlow 调优经验
    subagents=SUBAGENTS,                  # 下表
    middleware=[audit_mw, routing_mw],    # 4.1.2
    interrupt_on=INTERRUPTS,              # 4.5
    checkpointer=postgres_saver,          # 4.6
)
```

**子代理规划（专家岗位）**：

| 子代理 | 工具集（受限） | 模型档位 |
|---|---|---|
| general-purpose | 全量（默认） | 主力档 |
| uav-ops（巡检/飞行执行） | 调度/航线/飞前/飞行/排期 五域 | 主力档 |
| research（网页研究） | Playwright MCP + 搜索 | 便宜档 |
| doc-writer（交付物） | 文件系统 + 文档技能 + execute | 主力档 |
| data-analyst | 文件系统 + execute + 媒体/告警域只读工具 | 便宜档 |

子代理受限工具集直接对应 DeerFlow deploy/config.yaml.example 里已验证的划分，平移即可。

**工具规模控制**：11 域约 60+ 工具全量挂 Lead Agent 会稀释命中率（评测集当年
调优即为此）。策略：Lead 只挂高频域 + `task` 派单；长尾域工具只挂对应子代理。
上下文压缩由 deepagents 内置 summarization 中间件兜底。

#### 4.1.2 自研中间件

- **audit_mw**：`wrap_tool_call` 钩子记录（who/tool/args摘要/结果状态/耗时）
  → 落审计表，延续 docs/07 三关鉴权中的操作关审计。
- **routing_mw**：按任务标签切模型（见 4.8）。

### 4.2 MCP 集成层

```python
# core/mcp.py（示意）
from langchain_mcp_adapters.client import MultiServerMCPClient

client = MultiServerMCPClient(load_mcp_config())   # 配置见下
mcp_tools = await client.get_tools()
```

- **配置生成器**：`mcp_config.json` 由现有 **Nacos 同步桥**改造输出（原来写
  `deerflow/extensions_config.json`，改为写本框架配置并触发热重载）。
  每项：`{"transport": "streamable_http", "url": ..., "headers": {"X-API-Key": ...}}`。
- **鉴权**：headers 静态注入替代 DeerFlow interceptors；对需要「身份链」的调用，
  由网关把用户身份写入 run 的 `context`，audit_mw 透传（docs/09 阶段1 声明式口径）。
- **热更新语义（修正 DeerFlow 踩坑）**：
  - 工具发现失败 → 指数退避重试 + 告警，**不缓存跳过**；
  - 配置文件变更（IP 漂移）→ 重建对应 server 的连接与工具集，进行中的 run 不受影响；
  - skills 目录变更 → 下一会话生效（P1 做热加载）。
- 每次 run 前做一次 `/healthz` 快检，失败域的工具本轮不挂载并在系统提示中声明，
  避免模型去摸不存在的工具（排障①的模型行为）。

### 4.3 Skills 层（交付物能力）

- 技能格式：**Agent Skills 标准**（SKILL.md frontmatter + 渐进式披露），
  deepagents 通过 `create_deep_agent(skills=["./skills/"])` 加载技能目录，
  官方声明遵循 agentskills.io 规范——与现有 8 个业务技能同构，**零改动迁移**。
- 文档四件套（R4 核心，评审后修订）：
  - **主路径：自写四技能**（python-pptx / python-docx / openpyxl / reportlab），
    模板对齐无人机业务报告样式，工期 3~5 天，**计入 M2 基线**；
  - ⚠️ anthropics/skills 的四个文档技能 license 明确禁止在 Anthropic Services
    之外保留副本、分发、制作衍生作品——**代码与文本一律不引入**（内部使用同样
    不合规），仅允许阅读其公开的 SKILL.md 组织方式作为规范参考。
- 技能执行依赖 `execute`（跑脚本），故 R4 依赖 4.4 的沙箱后端就位。

#### 4.3.1 技能管理子系统（Skill Manager，R15）

技能不再是部署时的静态目录，而是一个有生命周期的受管资产。设计对齐
**Agent Skills 开放标准**（agentskills.io 规范）与业界已成型的分发模式
（GitHub CLI `gh skill install` 的 repo/名称@tag/SHA 寻址 + pin 锁定），
不自造格式。

**① 存储模型**

- 技能库根目录（对象存储或本地盘）+ Postgres 元数据表：
  `skill(id, name, version, scope, status, source_type, source_url,
  pinned_ref, checksum, imported_by, reviewed_by, created_at)`；
- 技能包 = 标准目录结构（SKILL.md + scripts/ + references/ + assets/），
  入库时整体校验并计算校验和；
- **作用域**：global（所有人）/ tenant / user 三级，延续 docs/05 §6.1
  可见性矩阵的思路；同名技能按 user > tenant > global 遮蔽。

**② 导入通道（四种）**

| 通道 | 形式 | 处理 |
|---|---|---|
| 本地上传 | zip / 文件夹（管理页拖拽） | 解包 → 校验流水线 |
| GitHub 地址 | `https://github.com/owner/repo`（整仓或子目录，支持 `@tag` / `@sha` 锁定） | 服务端 clone/下载指定 ref → 扫描目录内所有含 SKILL.md 的技能 → 逐个入库，记录 `source_url + pinned_ref` |
| 任意外部 URL | 技能市场页面链接（如 skills.sh 条目）或 zip 直链 | 解析出底层 GitHub/压缩包地址 → 同上 |
| 内置精选源 | 预配置若干可信 repo（如社区 awesome-agent-skills 精选） | 管理页内浏览 + 一键导入 |

**③ 校验与安全审查流水线（导入必经，不可跳过）**

技能是「提示词 + 可执行脚本」的组合，属于**提示注入与任意代码执行的双重
供应链入口**，按外部输入对待：

1. 结构校验：SKILL.md frontmatter（name/description 必填）解析、目录规范、
   大小上限；
2. 静态扫描：脚本清单提取、危险模式检测（网络外联、越目录访问、危险命令）、
   SKILL.md 文本的注入模式启发式检查；
3. **默认 `pending` 状态**：扫描报告呈现给管理员，人工审核通过才置 `enabled`
   ——与 4.5 人在环同一治理哲学：机器初筛、人做放行；
4. 运行时兜底：技能脚本一律在 4.4 沙箱内执行（P0 受限目录、P1 容器），
   与宿主隔离——审核失误不等于失守。

**④ 启停、更新与版本**

- 启停 = 元数据 `status` 切换，不删文件；
- 更新：记录了 `source_url` 的技能可「检查更新」（对比远端 ref），更新生成
  新版本行，旧版本保留可回滚；`pinned_ref` 锁定的技能不自动更新；
- 每次变更写审计日志（谁导入/启用/更新，延续 R11 追责口径）。

**⑤ 与 Runtime 的装配（关键实现点）**

deepagents 的 `skills=` 在 agent 创建时按目录加载，因此：

- **会话开始时**，Skill Manager 按「发起人可见且 enabled 的技能集合」在会话
  工作区物化一个 `skills/` 目录（软链或拷贝），传给 `create_deep_agent`；
- 技能启停/导入对**新会话**即时生效，天然解决 DeerFlow「skills 不热重载」
  的痛点（排障②），进行中的会话不受扰动；
- 子代理可按岗位限定技能子集（如 doc-writer 只装配文档类技能）。

**⑥ 管理界面与 API**

- 前端（4.9 二开范围内）：技能列表页（名称/描述/来源/版本/状态/作用域）、
  导入对话框（上传 or 粘贴 URL）、SKILL.md 预览、审核队列页（管理员）；
- API：`GET/POST /skills`、`POST /skills/import`（body: url 或 zip）、
  `PATCH /skills/{id}`（启停/审核）、`POST /skills/{id}/check-update`。

### 4.4 文件系统与沙箱（分阶段）

| 阶段 | 方案 | 覆盖 |
|---|---|---|
| P0 | **`LocalShellBackend(root_dir=会话目录, virtual_mode=True)`**：宿主机受限目录 + 自带 `execute` 工具，加超时/资源限制（本机开发形态）。评审更正：`FilesystemBackend` 只有文件操作、**不提供 execute**，不能用于跑技能脚本 | R4 内部试用、R6 |
| P1 | Docker 沙箱后端：**官方没有现成实现**（官方沙箱集成仅 LangSmith Sandboxes / AgentCore / Daytona），需自研实现 `SandboxBackendProtocolV2`（每会话容器、预装 python + 文档库、文件系统挂卷），**单独估时 3~5 天**；替代：自托管 Daytona 可免自研 | 生产形态 |
| 记忆路由 | `CompositeBackend`：`/workspace` → 会话目录，`/memories` → StoreBackend（Postgres，跨会话） | R6 |

P0→P1 换 backend 实现，agent 组装代码不动（backend 可插拔），但 P1 自研件的工期要单列。

### 4.5 人在环（双层，语义不变）

1. **工具内 confirm_token（保留，最后防线）**：🔒 工具无 token 只登记待确认单，
   token 由审批服务 8205 签发——框架无关，换 harness 不受影响。
2. **框架层 interrupt_on（新增，体验层）**：对 🔒 工具配置 interrupt →
   LangGraph 暂停并持久化 → 网关把 interrupt 事件渲染为确认卡片
   （复用 8213 UI 服务页面）→ 用户批准 → 网关走审批服务换 token → resume 续跑。
   紧急白名单动作（docs/05）跳过 interrupt 直接放行，白名单校验仍在服务端。

双层的意义：interrupt 提供好的交互，confirm_token 保证即使框架层被绕过
（或未来接入其他宿主）安全语义依然成立。

### 4.6 持久化与长任务（R9）

- checkpointer：`PostgresSaver`——每步落库，进程重启后 run 可从断点恢复；
- store：`PostgresStore`——长期记忆（/memories）与用户偏好；
- 会话模型：`thread_id = 渠道:会话标识`（企微群/钉钉会话/Web 会话各自映射）；
- **后台 run worker（评审补充，R9 验收的必要件）**：checkpointer 只保证状态
  不丢，**不会**在进程重启后自动续跑进行中的 run——这是 LangGraph Server 任务
  队列提供的能力，自建网关必须自补：
  - run 生命周期落库（pending / running / interrupted / done / failed）；
  - 执行走独立 worker（asyncio task 池，P1 可换进程级队列）；
  - **网关启动时扫描 running 状态的 run，从 checkpoint 恢复续跑**；
  - 完成 / 需确认时经消息通道回推，不阻塞对话。

### 4.7 消息网关（自建，FastAPI）

- **Web**：`POST /threads/{id}/runs` + SSE 流式（对齐 agent-chat-ui 所需协议，见 4.9）；
- **企微/钉钉**：回调 webhook → 验签 → 映射 thread → 投递 run；
  流式降级为分段消息 + 完成时交付物链接；确认卡片用各平台交互卡片，
  点击回调 → 审批换 token → resume；
- 身份：渠道用户 ID → 统一身份表 →（阶段2 再上 OAuth 2.1，延续 docs/09 规划）。

### 4.8 模型路由（R8）

- 接入方式：DashScope OpenAI 兼容模式（官方确认 qwen3-max / qwen-plus /
  qwen-flash 支持 function calling 与 `parallel_tool_calls`）：
  `init_chat_model("openai:qwen3-max", base_url=兼容端点, api_key=DASHSCOPE_KEY)`
  ——注意 `api_key` 必须显式传；`tool_choice` / 严格 JSON schema 与 OpenAI
  原生存在细节差异，POC 时列差异清单。
- ⚠️ **兼容性风险（评审上调量级）**：deepagents 的系统提示与中间件按 Claude
  调优，社区 issue（deepagents#981）与第三方实测显示非 Anthropic 模型在
  「长系统提示 + 密集工具调用」下可能明显退化。M0 抽测必须包含**子代理并行
  task 派单**场景，并预设降级路径：Lead 不达标 → Lead 切 Claude、便宜档留
  Qwen 的**混合路由**。
- 档位策略：

| 档位 | 场景 | 示例 |
|---|---|---|
| 强 | Lead 规划、doc-writer | qwen3-max（M0 达标验证）/ claude（降级预案） |
| 便宜 | research、data-analyst、批量子任务 | qwen-flash 级 |

### 4.9 前端（R10）

- 基座：**agent-chat-ui**（MIT、活跃维护）二开；
- 需要自加的面板（借鉴已归档的 deep-agents-ui 的信息架构）：
  todo 计划面板、子代理活动流、工作目录文件浏览/下载、确认卡片
  （interrupt 渲染，嵌 8213 页面或原生重写）；
- 连接协议：agent-chat-ui 经 `@langchain/langgraph-sdk` 连接，**必须是实现
  LangGraph Server 协议的后端**。评审结论（关键更正）：
  - `langgraph` 库本身 MIT 免费，但 `langgraph dev`/`langgraph build` 背后的
    服务端运行时 `langgraph-api` 是 **Elastic License 2.0 + license key**，
    生产自托管**不是无条件免费**（免费额度政策现状不明）；
  - **定稿路线**：开发期用 `langgraph dev` 直连 agent-chat-ui（本地开发豁免、
    零成本、快）；**生产走自建协议端点**——用 MIT 的 langgraph 库自建服务，
    不受 ELv2 约束；
  - 自建范围（评审修正工作量）：不止三个端点——threads CRUD、runs/stream 的
    SSE 事件格式（values/updates/messages/interrupt）、thread state/history、
    resume 语义，**估 1~1.5 周**，与 4.7 网关合并实现；
  - 降低成本选项（M0 评估）：开源项目 **Aegra**（LangGraph Server 协议的
    drop-in 替代），若可用则从「自建」降为「引入 + 裁剪」。

### 4.10 新增能力设计（R16~R19，v0.5 纳入）

- **R16 知识库 / RAG**：文档上传（PDF/Word/Markdown）→ 解析切分 →
  PostgresStore + pgvector 入库（复用 4.6 持久化栈，不引新组件）；
  暴露 `search_knowledge` 工具挂 Lead 与相关子代理；管理页支持文档
  列表/删除/重建索引；作用域同技能（global/tenant/user）。重型优化
  （重排、混合检索）后置。
- **R17 可观测**：自托管 **Langfuse**（开源），LangGraph callback 原生
  集成；每 run 记录完整 trace（工具调用链、token/成本、时延），与
  audit_mw 的审计记录经 `run_id` 关联成完整证据链；自带成本看板。
- **R18 任务模板 / Playbook**：模板 = 预置 prompt + 参数槽 + 默认技能/
  子代理集合，与 R14 定时任务共用 `playbook` 表（cron 字段可空）；
  网关提供模板 CRUD 与「按模板发起 run」端点；前端模板库页。
- **R19 用户级连接器授权**：与 docs/09 身份阶段 2（OAuth 2.1）合并；
  `user_credential` 表加密存储 token，MCP 配置生成器按 run 发起人注入
  对应 headers；首期支持 2~3 个高频连接器（邮箱/日历），管理页提供
  连接/断开。

### 4.11 安全与治理（R11，全部延续现有设计）

- 三关鉴权（docs/07）：接入关（网关鉴权）/ 操作关（X-API-Key + 审计中间件）/
  回源关（MCP 服务端校验）——框架替换不改变任何一关；
- 对外服务化继续走 Higress，不经本框架；
- 紧急白名单、设备级操作锁均在 MCP 服务端，天然继承。

## 5. 关键流程示例（批量巡检 → 报告 PPT）

1. 企微内下达「巡查 A 片区并出周报 PPT」→ 网关建 thread → Lead Agent 规划 todo；
2. `task` 并行派单：uav-ops 子代理（查图斑→选机→航线→飞前检查）、
   data-analyst 子代理（拉取历史告警/媒体数据到 /workspace）；
3. uav-ops 触发 `dispatch_drone`🔒 → interrupt → 企微确认卡片 → 用户批准 →
   审批服务签 token → resume → 工具带 token 执行；
4. 任务完成后 doc-writer 子代理加载 pptx 技能，`execute` 生成周报 PPT 到 /workspace；
5. 网关回推消息 + 文件链接；关键结论写入 /memories（下次巡检沿用偏好）。

覆盖 R1/R2/R4/R5/R6/R7/R9 的一次全链路验证，作为 M2 验收场景。

| 过程实时接管 | Manus 式沙箱直播 + 用户中途暂停/插话纠偏 | LangGraph interrupt 原语天然支持「中途插话」，M2 确认卡片已覆盖最关键的干预点；浏览器直播画面投入大、场景弱 |
| 多模态输入 | 上传图片/PDF 直接理解（巡检照片问询） | deepagents 文件系统已支持多模态文件，Qwen-VL 可挂 data-analyst 子代理——**技术上已通**，等业务场景明确再排期 |
| 配额与成本核算 | per-user/租户 token 配额、成本归集报表 | R17 的 Langfuse 自带 token/成本统计，先用它看板，超限管控后置 |
| 会话/交付物团队共享、移动端 | 协作与端 | 企微/钉钉通道天然是「移动端 + 群协作」的替代入口，优先级低 |

### 10.3 结论

主干无结构性缺失；**知识库（R16）是唯一「所有主流产品都有而方案没有」的
一等能力**，建议必纳。R17 可观测是工程刚需、成本极低。两项合计 +5~6 天，
不改变架构（复用既有 Postgres/pgvector 与 LangGraph callback 机制）。

## 11. 通用化重构与用户体系（v0.6，2026-08-14，方向纠偏后实施）

用户明确要求框架必须通用（业务不得渗入核心）、支持多项目管理与消息留痕。
本节为当前实际架构，§3/§4 与此冲突处以本节为准。

### 11.1 项目（Project）抽象

```
projects/<name>/
  project.json     display_name / role_prompt（业务人格与纪律）/ locked_tools
                   （人在环工具）/ mcp_headers_env（header→环境变量映射，密钥不落盘）
                   / knowledge_scope / skills（可见技能组）
  mcp_config.json  本项目接入的 MCP（外部自建/公共开源，http/sse/stdio 任意传输）
  subagents.json   本项目的专家子代理编制（可选）
```

- 核心代码零业务词；系统提示 = 项目 role_prompt + 通用 CORE_PROMPT（规划/
  派单/诚实性/记忆纪律）；
- 每项目一个图（aegra.json 一行）= 一个 assistant_id，前端/网关切项目即切
  assistant；**新开项目 = 新建目录 + aegra.json 加一行，零代码**；
- 隔离粒度：独立工作区（.workspace/<项目>）、记忆命名空间
  （memories, 项目, 用户）、知识作用域（scope IN (项目, global)）、
  playbook/消息/线程均带 project 标记；
- uav（无人机）降级为首个项目实例，default 为通用助理项目。

### 11.2 用户体系

- **身份**：渠道用户自动登记 user_identity（channel+channel_user_id→user_id，
  role member/admin）；网关经 run context 传 user_id，Web 端取 Aegra 鉴权身份；
- **接入鉴权**：Aegra 挂 auth.py（AUTH_TOKENS=token:身份:角色，未配置=开发
  模式匿名；401 三态实测）；网关管理面 X-Admin-Token（渠道回调/审批/页面外壳
  豁免）；网关调 Aegra 用 AEGRA_TOKEN 服务令牌；
- **归属**：记忆按 (项目,用户) 隔离；审计表 user_key 到人；审批 decided_by +
  桥接 X-User-Id；消息留痕带 user_id；
- **权限**：APPROVAL_REQUIRE_ADMIN=1 时聊天口令审批仅 admin；管理台用户页
  可切角色。

### 11.3 消息留痕

gateway_message 表：渠道消息进/出双向、项目隔离、带 user_id；
/messages API + 管理台「消息记录」页。会话内部全量消息另由 Aegra
（threads/runs，Postgres）持久化，两层互补：一层渠道视角、一层运行视角。

### 11.4 守卫栈（借鉴 deepseek-harness guard）

LoopGuardMiddleware（重复同参调用检测，消息历史统计无实例状态）
+ ModelCallLimitMiddleware（run 级 80 次硬顶）+ 网关 600s 流超时。

### 11.5 下游身份传递（On-Behalf-Of，2026-08-14）

外部系统（如无人机平台）需要知道「是谁在操作」才能返回该用户自己的数据：

- **机制**：IdentityPropagationMiddleware 每次工具调用把用户身份写入
  contextvar → MCP 连接的 httpx_client_factory 发请求时附加
  `X-Acting-User: u<user_id>`（恒发）与 `X-On-Behalf-Of: <外部账号>`
  （external_identity 绑定表命中目标系统时发）；
- **配置**：mcp_config.json 的 server 加 `"identity_system": "<系统名>"` 即启用；
  绑定管理走网关 `GET/POST /identity/bindings`；
- **信任模型（阶段1）**：下游验服务级 X-API-Key（信任本框架）后接受身份声明，
  按该身份回源查询/鉴权；阶段2 升级 OAuth 2.1 token 交换。
  第三方 SaaS 用凭据代管模式（R19，用户存自己的凭据，按人注入）。
- **下游侧待办**：mcp-services 读取 X-On-Behalf-Of 并透传给无人机平台回源
  接口（其 docs/09 身份链设计的服务端半边，改动在无人机项目侧）。
